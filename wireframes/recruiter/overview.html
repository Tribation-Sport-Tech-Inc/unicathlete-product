History Storage & Project Archive

Work Contexts define where active data lives. This section defines what happens to that data over time, especially when a Recruiting Project is closed.

Preservation principle: nothing is lost unless the user explicitly chooses a permanent delete action. Saved athletes, pipeline records, project history, evaluations, notes, and archived projects remain available or recoverable by default.

Project Lifecycle

Projects have three states. Archive is the safe default when closing a project; delete is the only irreversible operation and must be a separate deliberate action.

ACTIVE

Active

In progress and editable. Scouts can update criteria, athletes, priority, stage, evaluations, notes, and results.

ARCHIVED

Archived

Closed and read-only. Preserves criteria, context, timeline, evaluations, notes, athlete outcomes, and results. Can be reactivated at any time.

DELETED

Deleted

Permanent removal. Requires a clear confirmation and is separate from closing or archiving.

Recruiting Project Work

Each Recruiting Project is one scouting assignment. It contains recruiting criteria, athletes who may fit those criteria, and the scout workflow used to make decisions on each athlete. In MVP this is the scout's own workflow; team collaboration is a future scale layer.

Recruiting Criteria

The description of the athlete the scout is looking for, such as position, level, age, location, performance profile, media, and other requirements.

Priority Levels

Priority is separate from pipeline stage. Stage answers where the athlete is in the process; priority answers how much focus the athlete deserves.

HIGH High Priority

Strong fit or urgent opportunity. Should appear first inside each pipeline stage.

MEDIUM Medium Priority

Worth active review, but not the top focus. Useful for follow-up queues and comparisons.

LOW Low Priority

Monitor or keep as backup. Still in the pipeline, but lower focus than stronger fits.

Required pipeline control: scouts must be able to filter and sort by priority within any stage, for example showing only High Priority athletes in Reviewing.

Lead Scout

The scout responsible for the athlete inside the project. A scout may assign themselves as Lead Scout when adding an athlete. The Lead Scout manages follow-up, pipeline movement, evaluation coordination, and final recommendation.

Can evaluate: Yes
Can initiate/request info: Yes, through scout-athlete requests
Can message athlete: Yes, through scout-athlete conversation
Can compare athletes: Yes
Can request collaborator review: Future scale feature

Collaborator Scouts

Post-MVP feature. Collaborator scouts can later support the Lead Scout with review, evaluation, comparison, and internal discussion.

Can evaluate: Yes
Can review linked request responses: Yes
Can compare athletes: Yes
Can leave internal notes: Yes
MVP status: Deferred until team collaboration is validated
Rules: - NEW can be unassigned. - REVIEWING and later require lead_scout_id. - priority_level = high / medium / low and can change independently from pipeline_status. - Pipeline views must support stage filtering plus priority filtering/sorting. - In MVP, the verified scout is the default Lead Scout. - Project members, collaborator reviews, and override rules are post-MVP.
